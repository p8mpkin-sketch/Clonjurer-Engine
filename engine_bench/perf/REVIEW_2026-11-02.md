## 2. 发现的真实问题

### 2.1 正确性回退（已修复）：长页缩放分带并行破坏逐值等价

**现象**：`tests/test_perf_equivalence.py::VisualScoreEquivalence` 失败；`bench.py` 里 `score_long`（权重 3）闸门 `ok=N`、记 0 分。

**定位**：失败只出现在"参考图命中缓存 + 新克隆图"这条修复循环常态路径上，且只在超长页（1440×9000、1440×16000）出现。差异热力图逐像素比对：多数像素偏 ±1，个别边缘像素偏到 192。评分明细（四舍五入后）仍相等，所以**分数看不出回退**，只有原始像素暴露。

**根因**：为提速，把"克隆大图等比缩放到 512 宽"手工拆成"先横向分 3 带并行、再纵向分 3 带并行"，并假设它与 PIL 一次 `im.resize` 逐字节相同。实测证明**该假设不成立**：

| 源图 → 目标 | 手工"先横后纵" vs 单次 resize | "先纵后横" vs 单次 resize |
|---|---|---|
| 1440×9000 → 512×3200（长页） | **偏 8/通道，555 像素** | 一致 |
| 1440×16000 → 512×5689（长页） | **偏 3/通道，581 像素** | 一致 |
| 1280×2000 → 512×800 | 一致 | 偏 1/通道，130 像素 |
| 375×812 → 512×1109 | 一致 | 偏 8/通道，1140 像素 |

PIL 的 `im.resize` 会**按长宽比在内部自选先横后纵还是先纵后横**（超长页多走纵优先），8 位中间图的取整次序因此不同；且不同 Pillow 版本的内部次序与并列判定各异。手工路径硬编码"先横后纵"，只在恰好与 PIL 同序时才逐字节相同——对本优化主打的长页，恰好不同序。v4.7.0 开发时用的旧 Pillow 碰巧同序，所以当时 39/39 过；换到 Pillow 13 就破了。

**修复**：单图缩放回退为一次 `_fit_width`（= 基线调用，逐值一致），删除分带代码与死函数 `_hband`/`_vband`。跨图并行解码、参考图内容缓存、评分/边缘/热力图三路并行等优化全部保留。`core/cloner_engine.py`，净 −47/+9 行。

**代价与收益**：`score_long` 从"3.55× 但记 0 分（输出错）"变为"2.65× 且 88.7 分（输出对）"。那段分带是在**错误结果**上换来的 ~0.9× 虚假提速。总分 82.1 → 97.9，测试 39/39。

### 2.2 系统性隐患：逐值闸门 vs 未钉版本的 C 库

`requirements.txt` 全是下界约束（`pillow>=10.0.0`、`numpy>=1.26.0`），而正确性闸门的判据是"与冻结基线**逐字节/逐值一致**"。基线是在某个具体 Pillow/numpy 版本下冻结的，任何复刻了 PIL/numpy **浮点内部行为**的优化，一旦底层库升版就可能逐值漂移——2.1 正是这么发生的。**逐值闸门与不钉版本的依赖本质上互相矛盾。**

值得澄清的是：并非所有复刻都脆弱。我把其余几处复刻直接对**当前** Pillow 13 验证：

| 复刻项 | 性质 | 对 Pillow 13 实测 |
|---|---|---|
| 边缘 IoU（复刻 `FIND_EDGES`+`MaxFilter`） | **纯整数卷积 + 阈值**，无浮点舍入 | 与实时 PIL **0 像素差**，稳健 |
| 文本 F2 指纹 | 整数编码 + 集合运算 | 稳健 |
| 校准网格统计 | float32 行内精确累加（部分和 < 2²⁴） | 稳健 |
| 快速 PNG 编码 | 无损，解码后像素必然相同 | 稳健 |
| **长页缩放分带** | **依赖 PIL 浮点重采样的内部趟序与 8 位中间取整** | **脆弱（已移除）** |

**原则**：复刻**整数/确定性**算法安全；复刻**库的浮点内部实现字节输出**脆弱。后者要么不做，要么把底层库钉死。

## 3. 优化后真实热点（profiling）

长页 score_long（1440×9000 克隆图，~7MB PNG）单图各步最小耗时：

| 步骤 | 耗时 | 能否再并行/再省 |
|---|---|---|
| PNG 解码（单图） | ~75 ms | 否。单图 PNG 无法分块并行解码；PIL 不支持 PNG 的 draft 降采样 |
| resize → 512 宽（单次） | ~55 ms | **不能在保证逐值等价的前提下并行**（见 2.1） |
| 评分（NCC/边缘/文本/热力图，参考图已缓存后） | ~20–30 ms | 已三路并行 |

**即 score_long 的地板是"解码 75ms + 缩放 55ms"**，两者都是 C 层单图操作。想在这里超过 ~2.7× 只能牺牲逐值可复现性（正是 2.1 的教训）。所以 2.65× 是这一项诚实的上限，微基准已基本触顶。真正的增量不在这条微基准里，而在**端到端流程**（下节）。

## 4. 改进方案（按确定性/收益排序）

### P0（本次已落地）
- **移除长页缩放分带并行，回退单次 resize**。修复正确性闸门，总分 82.1→97.9，测试 39/39。

### P1 · 钉死图像库版本，给逐值闸门一个稳定地基（强烈建议，低风险）
- `requirements.txt` 将 `pillow`、`numpy` 由下界改为**精确钉版**（例如 `pillow==13.0.0`、`numpy==2.5.4`，即本环境实测可过的版本），或改用兼容区间 `pillow~=13.0`。
- 理由：逐值闸门要求底层浮点行为稳定；不钉版本，下一次 `pip install` 又可能悄悄引入 2.1 类回退。这是 2.1 能发生的**根本原因**，必须堵上。
- 升级库时作为一次独立变更：先升版 → 跑 `loop.py` → 若某项逐值漂移，重新冻结 `baseline/` 或按 P2 放宽该项判据。

### P2 · 对"诊断类"输出改用容差判据，而非逐字节（中收益，中风险）
- 差异热力图（`diff_preview.png`/`fidelity_diff.png`）是**给人看的诊断图**，不参与分数。对它要求逐字节一致，等于让一张诊断图去卡住整个闸门——2.1 里 score_long 被判 0 正是这么来的。
- 建议：闸门对**参与分数的输出**（评分明细数值）保持逐值；对**不参与分数的诊断图**改为"解码后像素最大偏差 ≤ 1、且偏差像素占比 ≤ 0.1%"的容差判据。这样既保住分数可复现，又不会被一张热力图的 ±1 噪声绑架，同时允许将来在热力图生成上做无损于视觉的加速。

### P3 · 评分时顺带算出克隆图校准网格，省掉校准阶段的二次解码（高端到端收益，需新建等价夹具）
- 现状：修复循环里，克隆图在**评分**阶段解码+缩放一次，紧接着**像素校准**阶段又把同一张克隆图**重新解码**一次（又是 ~75ms）。
- 建议：评分解码克隆图后，顺手把校准所需的网格统计一并算出缓存，校准阶段直接取用，省掉这次整页 PNG 二次解码。
- 收益：真实流程每轮每任务省一次 ~75ms 解码（微基准不体现，端到端显著）。
- 风险/成本：触及评分与校准两模块的接口，需为"评分顺带产出的校准统计"新增一条差分等价夹具（对齐现有 `pixel_calibrator` 逐值输出）后再并线。v4.7.0 文档第 9 节也点了这个方向，但当时未做。

### P4 · 把"是否走分带/并行"做成随库验证的可选加速（可选，仅在确有长页吞吐压力时）
- 若将来长页批量吞吐成为瓶颈，可重新引入缩放并行，但**必须**：进程启动时用几张代表性尺寸，实测"手工分带结果 == 当前 PIL 单次 resize"，一致才启用、不一致自动回退单次 resize。即把 2.1 的脆弱假设变成**启动期自检**而非硬编码。非必要不建议，徒增复杂度。

### P5 · 补充跨库版本的 CI 自检（流程，低成本）
- 在 `loop.py` 输出里带上 Pillow/numpy 版本号并写入 `history.jsonl`；若某轮闸门失败，版本号能一眼看出是否因升库所致。
- 可选：加一条冒烟用例，对**实时 PIL**（而非仅冻结基线）校验整数类复刻（边缘/校准），确保升库后这些仍 0 偏差。
